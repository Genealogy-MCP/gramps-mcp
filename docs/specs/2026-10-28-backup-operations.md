# Spec: Gramps Web API 3.24 pin and backup operations

Status: ready-for-agent. Date: 2026-10-28. Tracking issue: #108.

## Problem Statement

Gramps Web 26.10.2 (gramps-webapi 3.24.0) can create and list server-side
backups of a tree through its REST API. gramps-mcp is pinned to webapi
3.16.0 and has no backup operation, so an LLM working through the MCP
has no way to take a restore point before a batch of writes. Users who
run many agents in parallel against one tree take a backup by hand, out
of band, or not at all.

The pin itself is stale. 3.23 removed the `oql` list parameter the
resource table still carries, and rejects objects with unknown keys,
which the upsert operations have never been checked against.

## Solution

Two deliveries, in order.

1. Move the schema pin from 3.16.0 to 3.24.0 and prove the existing 20
   operations still pass against grampsweb 26.10.2.
2. Add two operations that wrap the backup endpoints one to one:
   `create_backup` (POST, wait for the async task, return the new
   backup's id and manifest) and `list_backups` (GET, newest first,
   optional client-side `limit`).

Nothing else. Restore, delete and download stay manual (the Gramps Web
UI, or the raw API). The MCP wraps the API thinly and does not invent
workflows around it.

## User Stories

1. As an LLM operator, I want to call `create_backup` before a run of
   upserts, so that a bad batch can be rolled back from a known point.
2. As an LLM operator, I want `create_backup` to block until the server
   task finishes, so that the returned id refers to a backup that exists.
3. As an LLM operator, I want `create_backup` to return the backup id and
   the manifest's creation timestamp, so that I can record it in my own
   journal.
4. As an LLM operator, I want `list_backups` to return backups newest
   first, so that the most recent restore point is first in the output.
5. As an LLM operator, I want `list_backups` to accept a `limit`, so that
   a tree with thousands of backups does not flood my context.
6. As an LLM operator, I want each listed backup to show id, size,
   restorable flag and creation time, so that I can pick one without
   downloading it.
7. As an LLM operator, I want a clear error when the server has no
   backup directory configured, so that I know the fix is server-side.
8. As an LLM operator, I want a clear error when my account lacks the
   backup permission, so that I ask for the right role instead of
   retrying.
9. As an LLM operator, I want a clear error when the per-tree rate limit
   is hit, so that I back off instead of looping.
10. As an LLM operator, I want `search` to find both operations by the
    keyword "backup", so that discovery works the same as for every
    other operation.
11. As a maintainer, I want the schema pin at 3.24.0 with the snapshot
    regenerated by the existing script, so that the resource table
    matches what the server serves.
12. As a maintainer, I want the removed `oql` parameter gone from the
    resource table, so that the table only offers parameters the server
    accepts.
13. As a maintainer, I want every upsert integration test to pass on
    26.10.2, so that the stricter unknown-key check is proven harmless.
14. As a maintainer, I want the integration compose to run 26.10.2 with
    a backup directory shared by web and worker, so that backup tests
    run in CI.
15. As a maintainer, I want the pin bump merged before the backup
    operations, so that a regression in the bump is isolated from new
    code.
16. As a maintainer, I want the operation count derived from the
    registry, so that adding two operations changes no hardcoded number.
17. As a maintainer, I want the README and CHANGELOG to list the new
    operations and the new server prerequisite, so that users know a
    backup directory must be configured.

## Implementation Decisions

- Two merge requests, sequential. MR 1 is the pin bump alone. MR 2 adds
  the backup operations on top of MR 1.
- MR 1: `SCHEMA_VERSION` becomes `3.24.0`; the OpenAPI snapshot and its
  sidecar are refreshed from the 26.10.2 test instance with the existing
  schema-fetch target; the resource table is regenerated and `oql` is
  removed; the integration compose pins grampsweb 26.10.2 for web and
  worker and adds a backup directory on the shared volume anchor with
  `GRAMPSWEB_BACKUP_DIR` pointing at it. The upsert operations are not
  changed unless the 3.23 unknown-key rejection breaks a test, in which
  case the offending field is dropped from the payload, not renamed.
- MR 2: two registry entries in the `write` category for `create_backup`
  and in the `read` category for `list_backups`. Both are handwritten
  operations, same as the upserts and the report operations; they are
  not driven from the resource table because the backup endpoints are
  not entity CRUD.
- `create_backup` takes no parameters. It POSTs to the backups
  collection. On 202 it polls the task endpoint with the same wait
  helper the report operations use, then reads the backup id from the
  task result. On 201 it reads the id from the body. It returns the id
  and the manifest's `created` timestamp. The server prunes to
  `BACKUP_KEEP` after each create; the operation does not mention or
  manage that.
- `list_backups` takes an optional `limit` (default 20, maximum 200).
  The API has no pagination, so the operation slices the list client
  side after the GET. Output rows show id, size, restorable and the
  manifest's created timestamp. Truncation is reported the same way
  the search operations report it.
- Error mapping: HTTP 501 becomes "Server has no backup directory
  configured (BACKUP_DIR); ask the server administrator to set one."
  HTTP 403 becomes "Account lacks the ManageBackups permission; the
  Owner role or above is required." HTTP 429 becomes "Backup rate limit
  for this tree reached; the server allows N per day" with N read from
  the metadata endpoint when available. All three are returned as tool
  errors, never raised as protocol errors.
- Annotations: `create_backup` is `readOnlyHint=False`,
  `destructiveHint=False`, `idempotentHint=False`. `list_backups` is
  `readOnlyHint=True`. Both `openWorldHint=True`.
- Operation descriptions state the server prerequisite (backup
  directory configured, Owner role) and that the archive holds the
  tree, tree settings and user list but not media files.
- No restore, delete or download operation. No age-based pruning; the
  server only prunes by count.
- Version bump and CHANGELOG entry in each MR, per the release gate.

## Testing Decisions

A good test calls the operation through the `execute` meta-tool against
the Docker test instance and asserts on the returned text and on what
the server now reports, never on internal helper calls.

- MR 1 has no new tests. The gate is the existing unit and integration
  suite passing on 26.10.2, plus the existing version-pin test
  asserting 3.24.0.
- MR 2 integration tests (marked `integration`, Docker required):
  `create_backup` returns an id that `list_backups` then shows first;
  `list_backups` with `limit=1` returns one row and reports truncation;
  both fail with the permission message when run as a non-Owner user
  (the compose already provisions an owner; add an editor for this
  case or skip with a reason if provisioning is out of reach).
- MR 2 unit tests (no network): output shaping for both operations from
  canned API payloads; error mapping for 501, 403 and 429; parameter
  validation rejecting `limit` outside 1..200.
- Prior art: the report operations' integration tests exercise the same
  task-polling path; the search tests show the truncation assertion
  shape; the error-formatting unit tests show the error shape.

## Out of Scope

- Restore, delete and download of backups.
- Any pruning beyond what the server does by count.
- Other 3.24 endpoints (structured query, per-object history, tree
  verify, server metadata, anniversaries). Separate specs if wanted.
- Server deployment and configuration. The spec names the prerequisite;
  setting it is the administrator's job.

## Further Notes

- The backup archive is an uncompressed tar holding a gzipped Gramps
  XML export, tree settings and the user list without credentials.
  Media files are not included.
- Backup ids are UUIDs assigned by the server. The MCP never generates
  or parses them.
- Since 3.24, tasks that change a tree do not run concurrently on the
  server. A `create_backup` issued while a report or another backup is
  running waits in the queue; the poll timeout should allow for that.
