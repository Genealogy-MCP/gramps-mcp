# Spec: Gramps Web API 3.24 pin and backup operations

Status: ready-for-agent. Date: 2026-10-28. Tracking issue: #108.
Reviewed by one critic pass (PR-1 rating M); its twelve change requests
are folded in below.

## Problem Statement

Gramps Web 26.10.2 (gramps-webapi 3.24.0) can create and list server-side
backups of a tree through its REST API. gramps-mcp is pinned to webapi
3.16.0 and has no backup operation, so an LLM working through the MCP
has no way to take a restore point before a batch of writes. Users who
run many agents in parallel against one tree take a backup by hand, out
of band, or not at all.

The pin itself is stale. 3.23 removed the `oql` list parameter the
resource table still carries, and rejects objects with unknown keys,
which the upsert operations have never been checked against.

## Solution

Two deliveries, in order.

1. Move the schema pin from 3.16.0 to 3.24.0 and prove the existing 20
   operations still pass against grampsweb 26.10.2.
2. Add two operations that wrap the backup endpoints one to one:
   `create_backup` (POST, wait for the async task, return the new
   backup's id and manifest) and `list_backups` (GET, newest first,
   optional client-side `limit`).

Nothing else. Restore, delete and download stay manual (the Gramps Web
UI, or the raw API). The MCP wraps the API thinly and does not invent
workflows around it.

## User Stories

1. As an LLM operator, I want to call `create_backup` before a run of
   upserts, so that a bad batch can be rolled back from a known point.
2. As an LLM operator, I want `create_backup` to block until the server
   task finishes, so that the returned id refers to a backup that exists.
3. As an LLM operator, I want `create_backup` to return the backup id and
   the manifest's creation timestamp, so that I can record it in my own
   journal.
4. As an LLM operator, I want `create_backup` to warn me that the server
   prunes old backups to a fixed count, so that I do not assume every
   restore point lives forever.
5. As an LLM operator, I want `list_backups` to return backups newest
   first, so that the most recent restore point is first in the output.
6. As an LLM operator, I want `list_backups` to accept a `limit`, so that
   a tree with thousands of backups does not flood my context.
7. As an LLM operator, I want each listed backup to show id, size,
   restorable flag and creation time, so that I can pick one without
   downloading it.
8. As an LLM operator, I want a clear error when the server has no
   backup directory configured, so that I know the fix is server-side.
9. As an LLM operator, I want a clear error when my account lacks the
   backup permission, so that I ask for the right role instead of
   retrying.
10. As an LLM operator, I want a clear error when the per-tree rate limit
    is hit, so that I back off instead of looping.
11. As an LLM operator, I want a clear error when the server is older
    than webapi 3.24, so that I do not read a generic not-found as a
    missing record.
12. As an LLM operator, I want `search` to find both operations by the
    keyword "backup", so that discovery works the same as for every
    other operation.
13. As a maintainer, I want the schema pin at 3.24.0 with the snapshot
    regenerated by the existing script, so that the resource table
    matches what the server serves.
14. As a maintainer, I want the removed `oql` parameter gone from the
    resource table, so that the table only offers parameters the server
    accepts.
15. As a maintainer, I want every upsert integration test to pass on
    26.10.2, so that the stricter unknown-key check is proven harmless.
16. As a maintainer, I want the integration compose to run 26.10.2 with
    a backup directory shared by web and worker, so that backup tests
    run in CI.
17. As a maintainer, I want the pin bump merged before the backup
    operations, so that a regression in the bump is isolated from new
    code.
18. As a maintainer, I want every place that hardcodes the operation
    count or order updated in the same change, so that the suite is
    green when the two operations land.
19. As a maintainer, I want the README, CLAUDE.md coverage table, CONTEXT
    glossary and CHANGELOG to list the new operations and the server
    prerequisite, so that users know a backup directory must be
    configured and which server version they need.

## Implementation Decisions

### Delivery shape

- Two merge requests, sequential. MR 1 is the pin bump alone. MR 2 adds
  the backup operations on top of MR 1.
- Version bump and CHANGELOG entry in each MR, per the release gate.

### MR 1: pin bump

- Order of operations, because the fetch script reads the compose image
  for its sidecar: first pin both grampsweb services in the test compose
  to 26.10.2 by sha256 digest, then run the schema-fetch target with the
  version-mismatch override, then set `SCHEMA_VERSION` to `3.24.0`, then
  regenerate the resource table with codegen. All in one change.
- If the 3.24 person schema changed, codegen fails with its schema
  error; update the person-schema field list in the resource policy and
  rerun. The unit test that checks hand-written models against the
  snapshot is the detector for the 3.23 unknown-key rejection; read its
  failures before touching any payload.
- `oql` must not appear in the regenerated table. If the 3.24 OpenAPI
  document still lists it, add an exclusion in the resource policy. Never
  hand-edit the generated table; codegen's check mode fails CI on drift.
- The upsert operations are not changed unless the unknown-key rejection
  breaks a test. The PUT path merges the existing object into the
  payload, so a server-computed key can round-trip. If a rejected key is
  server-computed or merely echoed, drop it from the payload. If it
  carries user-supplied data, stop and escalate; do not drop it silently.
- Test compose: add a named backup volume to the shared volume anchor so
  web and worker both see it, declare it at top level, and set on the
  shared env anchor `GRAMPSWEB_BACKUP_DIR` pointing at the mount,
  `GRAMPSWEB_RATE_LIMIT_BACKUP` to a high explicit value (the test
  Redis lives as long as the container, so repeated local `pytest -k
  backup` runs would otherwise hit the per-tree limit), and
  `GRAMPSWEB_BACKUP_KEEP` to an explicit value large enough that pruning
  cannot race the create-then-list test.
- Provision an Editor-role test user in the seed script alongside the
  existing owner, with its credentials as constants in the test env
  module. MR 2's permission test needs it.

### MR 2: backup operations

- Two handwritten registry entries, in a new tools module (the analysis
  module is near the file-size limit). `create_backup` in the `write`
  category, `list_backups` in `read`. They are not driven from the
  resource table because the backup endpoints are not entity CRUD. Add
  the two `ApiCalls` members and their mapping entries the same way the
  report operations are declared; task polling reuses the existing wait
  helper, imported from the analysis module.
- Registry flags: `create_backup` is `read_only=False`,
  `destructive=False`; `list_backups` is `read_only=True`,
  `destructive=False`. The registry has no idempotent or open-world
  field; those hints sit on the `execute` meta-tool. `create_backup` is
  not marked destructive because the count-based prune is server
  policy, not something the operation chooses; its description carries
  the warning instead (next point).
- `create_backup` takes no parameters. It POSTs to the backups
  collection. The client does not surface the status code, so branch on
  body shape as the report operations do: a body with a task id means
  202, poll the task endpoint with the shared wait helper and a 300 s
  timeout (3.24 serializes tree-changing tasks, so a backup can queue
  behind a report), then read the backup id from the task result
  object; a body with a backup id means 201, use it directly. Confirm
  the exact key names against the `/api/backups` schemas in the
  refreshed snapshot. Return the id and the manifest's created
  timestamp. The operation description must say that the server keeps
  only the newest `backup_keep` backups per tree and prunes the rest
  after every create, quoting `backup_keep` from the metadata endpoint
  when available, so that parallel agents do not assume an earlier
  restore point survives. The 201 path is covered by unit tests only;
  the test compose always runs a worker, so integration sees 202. That
  is accepted.
- `list_backups` takes an optional `limit` (default 20, maximum 200).
  The API has no pagination, so the operation sorts client side by the
  manifest's created timestamp descending, ties broken by id, then
  slices. Output rows show id, size, restorable and created timestamp.
  Truncation is reported the same way the search operations report it.
- Error mapping needs one client change: `GrampsAPIError` gains a
  `status_code` attribute, set in the HTTP-status branch of the request
  helper. The backup handlers map on that attribute, never on message
  text. HTTP 501 becomes "Server has no backup directory configured
  (BACKUP_DIR); ask the server administrator to set one." HTTP 403
  becomes "Account lacks the ManageBackups permission; the Owner role or
  above is required." HTTP 429 becomes "Backup rate limit for this tree
  reached; the server allows <rate_limit_backup>" with the raw limit
  string echoed from the metadata endpoint, no assumption about its
  unit. HTTP 404 on the backups collection becomes "Server is older
  than gramps-webapi 3.24 and has no backup endpoints"; the existing
  not-found message would otherwise point at a record lookup. All four
  are returned as tool errors, never raised as protocol errors.
- Operation descriptions state the server prerequisites (webapi 3.24 or
  newer, backup directory configured, Owner role) and that the archive
  holds the tree, tree settings and the user list without credentials,
  but no media files. The README repeats the prerequisites and notes
  that the archive stores the user list on server disk.
- Every hardcoded operation count or order moves with this change: the
  operations test's expected set, total of 20 and per-category counts
  (read becomes 4, write 11), the registry-build test's expected order,
  the meta-tools test's "20 operations" string, and the operation order
  list in the operations module, which the registry merge requires to
  name every operation. The health endpoints already derive the count
  and need nothing. README (which still says 19), the CLAUDE.md coverage
  table and the CONTEXT glossary's snapshot version are updated.
- No restore, delete or download operation. No age-based pruning; the
  server only prunes by count.

## Testing Decisions

A good test calls the operation through the `execute` meta-tool against
the Docker test instance and asserts on the returned text and on what
the server now reports, never on internal helper calls.

- MR 1 has no new tests. The gate is the existing unit and integration
  suite passing on 26.10.2, the version-pin test asserting 3.24.0, and
  codegen's check mode passing.
- MR 2 integration tests (marked `integration`, Docker required):
  `create_backup` returns an id that `list_backups` then shows first;
  `list_backups` with `limit=1` returns one row and reports truncation;
  both operations return the permission error when run as the Editor
  user. Switching user means overriding the username and password
  settings and clearing the cached settings singleton; check whether the
  auth module caches a token at module level and clear that too. CI has
  the docker CLI, so provisioning is reachable and there is no skip.
- MR 2 unit tests (no network): output shaping for both operations from
  canned API payloads covering the 201 body, the 202-plus-task-result
  path and the list body; error mapping for 501, 403, 429 and 404 via
  `status_code`; parameter validation rejecting `limit` outside 1..200.
- Prior art: the report operations' integration tests exercise the same
  task-polling path; the search tests show the truncation assertion
  shape; the error-formatting unit tests show the error shape; the
  operations test shows the registry-count assertions.

## Out of Scope

- Restore, delete and download of backups.
- Any pruning beyond what the server does by count.
- Other 3.24 endpoints (structured query, per-object history, tree
  verify, server metadata, anniversaries). Separate specs if wanted.
- Server deployment and configuration. The spec names the prerequisite;
  setting it is the administrator's job. Upgrading a live server to
  26.10.2 is a one-way tree migration and is the administrator's call.

## Further Notes

- The backup archive is an uncompressed tar holding a gzipped Gramps
  XML export, tree settings and the user list without credentials.
  Media files are not included.
- Backup ids are UUIDs assigned by the server. The MCP never generates
  or parses them.
- Everything in both MRs reverts cleanly with git; no data migration is
  involved on the MCP side.
